# タスク整理 (Issue化の元ネタ)

`AIとやりとりした履歴.md` の要件を、GitHub Issue に落とせる粒度へ分解したもの。
Issue 化が完了したら、このファイルは削除するか索引として残す。

タスクIDはセクション別(`M1-3` など)。タスクを追加しても既存の番号がずれないようにしている。

## 基本方針

> 最初から巨大な AI Platform を作らない。今必要な **MRレビュー自動化** を作る。
> ただし各部品(GitLab Adapter / Workspace / Runner / Store / Job)は、
> 将来の Issue→設計→実装→MR へそのまま成長できる境界で切る。

前提(履歴ドキュメントより):

- 実装言語は **Python で確定**(Windows・管理者権限なし・外部DL制限ありのため依存は最小限)
- GitLab は **REST API のみ**(MCP・glab 不可)。ただし将来 MCP へ差し替え可能な抽象を置く
- LLM は **Claude Code (ヘッドレス) → Amazon Bedrock**。Bedrock API を直接叩く実装は極力書かない
- Windows = 人間の対話・レビュー / Linux・Docker = 無人AI処理

## マイルストーン

| ID | 名前 | ゴール |
|----|------|--------|
| M0 | 土台整備 | 開発を始められる状態(構成・設定・ログ・CI) |
| D  | ドキュメント | 体系だったドキュメント。人間とAIの両方が読める形で維持する |
| S  | Spike | 先に潰すべき技術的不確実性の検証 |

| X  | 横断 | セキュリティ・コスト・可観測性 |

## D. ドキュメント

### 読み手を4つに分ける

このプロジェクトのドキュメントは、単なる備忘録ではない。

| 読み手 | 誰 | 置き場所 |
|--------|-----|----------|
| **作る人** | このリポジトリの開発者 | `docs/` 直下・`adr/`・`specs/` |
| **使う人** | レビュアー / 実装者(MRを出す側) / Issue起票者 | `docs/guide/` |
| **動かす人** | 導入・設定・障害対応をする人 | `docs/operations/` |
| **Claude Code 自身** | AI Runner | `CLAUDE.md`・`docs/specs/` |

当面は全部同一人物だが、**文書は最初から分けておく**。社内展開時に「使う人」向けだけを切り出せる。

利用者向けドキュメントが特に重要な理由:

- **実装者(MRを出す側)への周知** — AIの指摘はGitLabに自動投稿しない方針だが、
  それが伝わっていないと「勝手にAIに見られてコメントされる」という不安を生む。何をする/しないかの明示が要る
- **Issue起票者への手引き (M4)** — Issueの曖昧さは `WAITING_HUMAN` での停止や誤った仮定に直結する。
  「AIが実装できるIssueの書き方」は、ドキュメントでありながら**精度を上げる施策そのもの**
- **過信の防止** — 最終判断は人間、が前提の設計。AIレビューが何を見逃すかを明文化しないとこの前提が崩れる

そして **Claude Code 自身が読み手**であるため、仕様書は散文ではなく
**構造化された・参照可能な粒度**で書く。曖昧な仕様書は「AIが勝手に推測する問題」(履歴ドキュメント §5)を
直接悪化させる。

## M2. 実運用強化

**M2-1. 並列レビュー実行**
ワーカープール、同時実行数の設定、worktree/DBの競合回避、失敗時の隔離。
`area/runner` `prio/P1`

**M2-2. 再レビュー対応**
新規 push 検出時の再実行。前回の指摘を引き継ぎ、「修正済み / 未対応 / 新規」を区別する。
`area/review` `prio/P1`

**M2-3. レビュー結果の確認UX**
レビュー待ちMR一覧と結果を素早く見る導線(索引Markdown or 簡易TUI)。
VS Code の GitLab 拡張を最終レビューUIとして併用する前提で、そこに繋がる形にする。
`area/cli` `prio/P1`

**M2-4. 追加調査モード**
対象MRの worktree で対話型 Claude Code をワンコマンド起動。人間が深掘りするための導線。
`area/cli` `prio/P1`

**M2-5. GitLabへの選択的コメント投稿** (要否は M2 着手時に判断・保留中)
AIの指摘を自動投稿はしない。人間が選んだ指摘だけを投稿するフロー(確認必須)。
当面は結果を見ながら人間が手打ちでコメントする運用でも足りる可能性があり、
M2着手時にその運用の負荷を見てから要否を判断する。
`area/gitlab-adapter` `prio/P1`

**M2-6. 指摘の重要度分類とフィルタ**
critical / major / minor。既定表示を絞り、ノイズを人間に見せない。
`area/review` `prio/P1`

**M2-7. レビュー品質の評価とプロンプト改善ループ**
既知のMRをサンプルセット化し、プロンプト変更時の回帰(見逃し/ノイズ)を比較できるようにする。
`area/review` `prio/P1`

**M2-8. 可観測性: 実行履歴とエラーの可視化**
Job履歴、失敗理由、所要時間、リトライ状況。
`area/infra` `prio/P1`

**M2-9. レビュー完了通知**
完了を人間に知らせる(デスクトップ通知 / ファイル / 任意のチャネル)。
`area/infra` `prio/P2`

**M2-10. GitLab Adapter: Issue/MR操作の拡充(取得・作成・更新)**
現在の許可リスト(M1-1)はMRの読み取り・作成・コメントのみで、Issueの読み取り・作成・更新、
MRの更新が存在しない。`list_issues` / `get_issue`(読み取り)、`create_issue` / `update_issue`
(書き込み)をProtocol/REST実装に追加する。あわせてMR側にも `update_merge_request`(書き込み)
を追加する。書き込みは引き続き許可リスト方式を維持し、merge・クローズ・削除等は含めない
(必要になれば個別に追加を検討する)。
`area/gitlab-adapter` `prio/P0`

**M2-11. 要件→Issue分解ワークフロー(CLI・対話型)**
大きな開発要件を人間とClaude Codeの対話で複数のGitLab Issueへ分解し、M2-10のAdapterを
使って起票する。M4のIssue駆動パイプライン(既にあるIssueが前提)より前段の工程であり、
要件の切り方には人間の判断が本質的に必要なため、無人実行のM4(Linux/Docker)ではなく
Windows・対話型のCLIで提供する(`docs/requirements.md` 3-C参照)。
`area/cli` `prio/P1`

**M2-12. Claude CodeからGitLab操作を呼び出すツールブリッジ**
対話型Claude Code(Windows VS Code拡張・CLI)が、GitLab Adapterの許可された操作(read全般 +
Issue/MR作成・更新・コメント)をエージェント自身のツールとして呼び出せるようにする。
Claude Code Runner(M1-7)がMRの情報を静的なプロンプト文字列として埋め込む方式とは別の経路で、
Claude Codeの実行中にエージェントが能動的に呼び出す口を指す。GitLab AdapterをMCPサーバーとして
ラップし、Claude Code起動時に`--mcp-config`で渡す方式が有力候補(具体化はADRで判断する)。
M2-4(追加調査モード)・M2-11(要件→Issue分解ワークフロー)が前提とする「対話型Claude Code
からのGitLab操作」の実現基盤となる。
`area/gitlab-adapter` `area/cli` `prio/P0`
